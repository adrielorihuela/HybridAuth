**`hybridauth.command.*` permissions now work on their own.** Granting
`hybridauth.command.server` or a shortcut's `hybridauth.command.server.<server>` in LuckPerms could
do nothing at all, and the only way round it was to set the old `velocity.` or `hybridvelocity.`
node instead. That is fixed. This release also retires the fork's old names, which needs **a
minute of your attention before you upgrade** — see [Action required](#action-required) below.

## Permissions that do what they say

`/server` and the per-server shortcuts (`/lobby` and the rest of `comandos`) are allowed for
everyone unless a permission says otherwise. Each one used to look at its `hybridauth.command.`
node, its `velocity.command.` node and its `hybridvelocity.command.` node, and refuse the command if
**any** of them was false.

That sounds harmless, but a permissions plugin answers for every node it is asked about. If
anything in LuckPerms made `velocity.command.server` false for a player — a default group carried
over from stock Velocity, a `velocity.command.*` wildcard, a leftover from an earlier setup — then
granting `hybridauth.command.server` to that player changed nothing. The grant was there; it simply
lost to a node you were not looking at, with no message anywhere to say so. Setting the `velocity.`
node to true worked, because then nothing said false any more, which is exactly what was reported.

Now the rule is the same for every command the proxy has:

1. If the `hybridauth.command.` node is set, **true or false, it decides**.
2. If it is not set, upstream's `velocity.command.` node decides, so a permission set up for stock
   Velocity keeps working.
3. If neither is set, `/server` and the shortcuts are allowed, and the administrator commands
   (`/send`, `/glist`, `/hybridauth reload` and the rest) are not.

So `hybridauth.command.*` always wins, and having both set is never a conflict. Every combination is
covered by tests, for `/server` and for a shortcut.

**One more thing that may have caught you out:** the shortcut guide told LuckPerms users to write
`-hybridauth.command.server.lobby`. LuckPerms does not read a leading `-` as "deny"; it creates a
separate node with a dash in its name that nothing ever checks. The guide now gives the commands
that actually work:

```
lp group default permission set hybridauth.command.server.lobby false
lp group vip permission set hybridauth.command.server.lobby true
```

Full details: [docs/guide/server-commands.md](https://github.com/adrielorihuela/HybridAuth/blob/main/docs/guide/server-commands.md#permissions).

## Two names instead of five

The fork has been called `velocity`, `hybridvelocity` and `hybridauth`, and kept every one of them
working, plus the short `/ha` and `/hv`. From this release there are only two: **`hybridauth`**, the
fork's own, and **`velocity`**, upstream's, so that dropping this jar into a stock Velocity
installation still just works.

| Gone | Use instead |
| --- | --- |
| `/ha`, `/hv`, `/hybridvelocity` | `/hybridauth` or `/velocity` |
| `hybridvelocity.command.*` permission nodes | `hybridauth.command.*` |
| `hybridvelocity.toml` as the configuration file | `config/HybridAuth.toml` |

## Action required

Check these three things **before** replacing the jar:

1. **Commands.** If players, staff or other plugins run `/ha`, `/hv` or `/hybridvelocity`, change
   them to `/hybridauth` (or `/velocity`). The proxy no longer knows the old ones, so they go to the
   backend server like any other command it does not handle.
2. **Permissions.** `hybridvelocity.command.*` nodes no longer count for anything. Find them with
   `lp search` (for example `lp search hybridvelocity.command.reload`) and set the same node under
   `hybridauth.command.` instead — `lp group admin permission set hybridauth.command.reload true` —
   then unset the old one.
   Nodes under `velocity.command.` keep working and need no change.
3. **Configuration file.** If your configuration is still called `hybridvelocity.toml`, in `config/`
   or next to the jar, it is no longer picked up, and the proxy would start on a fresh default
   configuration instead. Rename it to `config/HybridAuth.toml` first. If you already have
   `config/HybridAuth.toml` — anyone who has started 1.2.0 or later does — there is nothing to do.

## Upgrading from 1.3.0

Do the three checks above, then replace the jar and start it. Nothing in `config/HybridAuth.toml`
changes, and `forwarding.secret` and the password database are left as they are.

If you had worked around the permission bug by setting `velocity.command.server…` nodes, they keep
working; you can now move them to `hybridauth.command.server…` and they will mean the same thing.
