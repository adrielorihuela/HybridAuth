**Portals can now lead to another server.** Step into the End portal in your lobby and arrive on
survival. The fork is also brought up to **Velocity 4.2.0**, which adds **Minecraft 26.3**.

## Portals that lead to another server

A new `[portales]` section sends players who go through a Nether or End portal on one server to
another server instead:

```toml
[portales]
lobby = {
    nether = "survival",
    end = "survival"
}
```

Either line can be left out, and that portal then works as it always did. To send only the End
somewhere else:

```toml
[portales]
lobby = {
    end = "Survival"
}
```

**Only the dimensions you list need enabling on the origin server** — `allow-end: true` in
`bukkit.yml` for `end`, `allow-nether=true` in `server.properties` for `nether`. The proxy never
sees a portal block; what it sees is the server moving the player into the Nether or the End, so a
dimension that is switched off never gets that far. Anything that moves a player there counts, not
only a portal.

Worlds are recognised by name: `minecraft:the_nether` and `minecraft:the_end`, and any world whose
name ends in `_nether` or `_the_end`, which covers Multiverse worlds such as `lobby_nether`.

**It is on in a new configuration**, with the entry above. The shipped `[servers]` has no
`survival` of its own, so a name that is not in `[servers]` — or a server pointing at itself — is a
warning at start-up and that portal is left alone, rather than an error that would stop the proxy
starting. Delete the entry if you do not want it. Names are not case-sensitive, and
`/hybridauth reload` picks up changes.

When it fires, the console says so:

```
<player> entered the end on lobby, sending them to survival
```

If the target cannot be reached, the player gets the usual "unable to connect" message and stays in
the origin server's Nether or End, exactly as if nothing were configured. The client and the server
never disagree about which world the player is in.

**One thing to plan for:** the origin server did move the player into its Nether or End, so the next
time they join it they will be there. On a lobby, use a plugin that sends players to spawn when they
join.

The entries are written as inline tables spanning several lines, which is TOML 1.1, so the
configuration is now read as TOML 1.1. Every file that was valid before still is. The one-line form,
`lobby = { nether = "survival", end = "survival" }`, works too.

Full details: [docs/guide/portal-redirects.md](https://github.com/adrielorihuela/HybridAuth/blob/main/docs/guide/portal-redirects.md).

## From upstream

Twenty-four commits from [PaperMC/Velocity](https://github.com/PaperMC/Velocity), covering the
4.2.0 release.

- **Minecraft 26.3.**
- **Ping passthrough is now a section of its own**, with a switch for each part of the response —
  version, player count, description, favicon and mod list — instead of the single
  `ping-passthrough` setting. Your existing choice is converted on the first start.
- **Clients that take too long to log in are disconnected**, and frame sizes are checked before
  login, closing two ways to tie up the proxy with connections that never finish.
- **The console is back on JLine's FFM terminal backend.** 1.2.1 moved it to JNI because FFM was
  crashing the JVM on window resize; that is fixed upstream, so it is back on the canonical choice.
- `/hybridauth reload` now removes servers deleted from the configuration, and the packet limiter
  can no longer grow without bound under a flood.
- Netty 4.2.19 and other dependency updates.

`velocity-api` is now published at `4.2.1-SNAPSHOT`, following upstream.

## From this fork

**A configuration fix that mattered more than it looks.** HybridAuth used to write its own numbers
into upstream Velocity's `config-version`, and corrects that on first start by handing the key back
to `2.8`. Velocity 4.2.0 is the first release to use `2.9` for real — for the ping passthrough
conversion above — and the fork had once written `2.9` itself. Left as it was, the correction would
have taken every genuine `2.9` back to `2.8`, and the next start would have run upstream's
conversion again over a section it had already converted. The two are now told apart by what the
file contains rather than by the number, and a test starts the proxy twice in a row to prove it.

**Releases are now built and published by CI** from `main`, so the jar attached here is the one the
build produced, with nothing in between.

## Known limitation

The authentication server, NanoLimbo, supports up to Minecraft 26.2, and so does NanoLimbo
upstream. An offline-mode player on a 26.3 client reaches it through ViaVersion's translation
rather than natively. Premium players are unaffected, since they never visit it.

## Upgrading from 1.2.1

Replace the jar and start it. `ping-passthrough` is converted to its new section by itself.

An existing configuration does not gain `[portales]` on its own. To use it, add the section from
above to `config/HybridAuth.toml`.
